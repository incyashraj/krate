# A Krate app cannot make an HTTPS request — FIXED, same day

Found on 2026-08-01 while looking for a third program to port. Recorded before
starting the port, because it disqualifies the entire network shape and there
is no point spending an hour discovering it the slow way.

## What is broken

A guest app can fetch `http://` and cannot fetch `https://`.

Measured, both on the same machine, with the same sample app
(`apps/krate-curl`) and the same grant:

```
http://127.0.0.1:8771/     -> "plain http ok"
https://example.com        -> "krate-curl: fetch failed"
```

The permission wall allows the HTTPS request. It is the fetch itself that
fails, so this is not a capability problem.

## Why

`crates/runtime/src/lib.rs` opens a raw `TcpStream` and writes HTTP request
framing by hand (`connect_tcp_on_host`, around line 1869). There is no TLS
anywhere in that path — no handshake, no certificate verification — so an
`https://` URL is parsed correctly, connected to on port 443, and then spoken
to in plaintext, which the server refuses.

The URL parser already understands `https` and defaults it to port 443, which
is why this looks supported from the outside.

## Why it matters more than it looks

Every API worth calling is HTTPS. A network app that can only reach plain HTTP
can talk to a local development server and nothing else on the internet — which
is exactly what the one sample app's manifest admits: it is scoped to
`net.connect:127.0.0.1:*`.

So **the network shape of Gate 4 cannot be ported at all** until this is fixed.
That is one of the six shapes, and it blocks the shapes built on it — anything
that signs in, syncs, or fetches data.

This is also the first defect found today that is genuinely the runtime rather
than the tooling. Six previous findings were all things the tools could not
see; this is a thing the runtime cannot do.

## What it would take

`ureq` is already a workspace dependency with TLS enabled — it is used by the
CLI, the bundle crate, and the port analyzer. So the library question is
settled; what is missing is the wiring from the guest's `net.connect` path to
it.

The work is not the handshake. It is deciding what the sandbox promises:

- **Certificate verification.** Must be on, and must not be something an app
  can turn off. An app that can disable verification can be told to disable it.
- **Which roots to trust.** The platform store differs on three operating
  systems, and "works on my machine" is exactly the failure Krate exists to
  remove. A bundled root set behaves identically everywhere and goes stale;
  the platform store is current and differs per machine. This is the real
  decision and it should be made deliberately.
- **What the capability means.** `net.connect:host:443` currently means "may
  open a socket". With TLS it should mean "may make a verified HTTPS request to
  this host", and a plain-HTTP connection to a host granted for HTTPS should
  probably be refused rather than silently downgraded.
- **Redirects.** A redirect can move a request to a host the app was never
  granted. Following one without re-checking the grant would be a hole straight
  through the permission wall.

That last point is the one to get right. It is not a big change, but it is a
security boundary, and doing it quickly is how a sandbox grows a hole.

## What shipped

Fixed the same day. `https://example.com` now returns its page to a guest app.

The parser records the scheme instead of refusing anything that is not
`http://`, and the host routes TLS requests through `ureq` -- the same stack the
CLI, bundle, and port crates already use, so there is one certificate story in
the workspace rather than two.

The four decisions, made rather than defaulted:

- **Certificates are always verified**, with no way for an app to ask
  otherwise. An app that can disable verification can be told to disable it.
- **Redirects are not followed** (`.redirects(0)`). A redirect can move a
  request to a host the person never granted, so following one silently would
  let any granted host hand the app somewhere else.
- **The response is bounded** by the same limit as plain HTTP, read one byte
  past it so an oversized body is refused rather than truncated.
- **The timeout is the caller's**, so a guest cannot be made to wait longer
  than the run allows.

Verified by hand: `https://example.com` returns its page; plain HTTP still
works; and a run granted `example.com` and asked for `iana.org` is refused, so
TLS did not punch a hole in the capability check.

The root store question was settled by using the same stack as the rest of the
workspace. If that choice is ever revisited it should be revisited everywhere
at once, which is the point of having one.
